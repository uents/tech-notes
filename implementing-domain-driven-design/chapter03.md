# コンテキストマップ

## コンテキストマップとは

- コンテキストマップは、複数の Bounded Contextが存在する場合に、それらの関係を視覚的に表現するためのツール
- コンテキストマップを使用することで、各 Bounded Context の役割や責任、そしてそれらがどのように相互作用するかを理解しやすくなる

## 空間の評価

- 問題空間の評価: ドメインエキスパートとの対話やドメインの分析を通じて、自然に浮かび上がってくるもの
- 解決空間の評価: ソフトウェアの境界として「設計する」もの

## コンテキストの関係性のパターン

- **パートナーシップ** (Partnership):
  - 2つの Bounded Context が対等な関係で協力する場合
  - 例: 注文管理と顧客管理が密接に連携している場合など
- **共有カーネル** (Shared Kernel):
  - 複数の Bounded Context が共有するモデルやコードなどの共通部分
  - 変更時にすべての Bounded Context に影響が及ぶ可能性があるため、設計の助けになることもあれば、逆に邪魔になることもある
- **顧客/供給者** (Customer/Supplier):
  - 下流の Bounded Context（顧客）を考慮して、上流の Bounded Context（供給者）が開発する関係
  - 上流側は下流側のニーズに応える義務がある
- **順応者** (Conformist):
  - 下流の Bounded Context（順応者）が、上流の Bounded Context のモデルをそのまま受け入れる関係
  - 下流側は上流側から与えられたモデルで我慢する必要がある
- **腐敗防止層** (Anti-Corruption Layer: ACL):
  - 2つの Bounded Context 間の翻訳層
  - 他方 Bounded Context のモデルを自分のモデルに翻訳することで、モデルの汚染を防ぐ役割を果たす
- **公開ホストサービス** (Open Host Service: OHS):
  - 他の Bounded Context が利用できるように、明確なインターフェースを提供する関係
  - 例: 上流側が公開APIを提供し、下流側が自由に利用できるようにする
- **公表された言語** (Published Language: PL):
  - 2つの Bounded Context 間で共有される言語
  - 例: 共通のデータ交換フォーマット（JSONスキーマなど）を定義し、複数の Bounded Context で使用する場合など
- **別々の道** (Separate Ways):
  - 2つの Bounded Context が完全に独立している関係
  - 例: 注文管理と在庫管理が全く異なるチームで開発され、相互作用もない場合など
- **巨大な泥団子** (Big Ball of Mud):
  - すべての Bounded Context が同じコードベースに存在し、明確な境界がない状態
  - 複数のドメインが混在し、責任の分離が不明確な場合など

> [!NOTE]
> * ここでの「上流」「下流」とは、誰が誰に影響を与えるかという関係性を指す。例えば、外部サービスが提供するAPIを利用する場合、外部サービスが上流で、自分たちが下流になることが多い
> * 上流・下流の関係性（誰が誰に影響を与えるか）を意識してパターンを選択することが重要。ACLは外部サービスや汎用サブドメインとの接続時に特に有効

## なぜパターンの概念を持ち込むのか？

- ACLやOHS/PLが必要なのは分かるが、そもそもシステム設計に精通していると直感的に抽象化層であったりAPIが必要というのは分かる
- 「直感で分かる」という状態は、チーム間では共有されない可能性がある

```
直感で分かる状態：
　「ここに抽象化層が必要だな」
　→ なぜ必要か・どの範囲か・誰が所有するかが設計者の頭の中にしかない

概念に名前をつけた状態：
　「ここにACLが必要だ」
　→ DDDを知っているメンバー全員が
　　・上流モデルの侵入を防ぐ層
　　・下流チームが所有する
　　・変換責務を持つ
　　といった意味を即座に共有できる
```

直感が言語化されると：

- 設計レビューで「これはACLになっているか」と具体的に議論できる
- 新しいメンバーが設計の意図を理解しやすくなる
- Agentic CodingでAIエージェントへの指示が明確になる

システム設計に精通している人には概念自体は自明です。DDDの語彙の価値は概念の発見ではなく共通言語化にある。

## ACL、OHS/PLの判断基準

- ACL：「上流から自分たちを守りたい」→ 下流主導
- OHS/PL：「複数の下流に標準的に提供したい」→ 上流主導

### ACL: 腐敗防止層

下流コンテキストが自衛のために設ける翻訳層。

- 選ぶ状況：
  - 上流が自分たちの都合でモデルを変えてくる
  - 上流との交渉力がない（Conformistになりたくない）
  - 上流のモデルがドメイン的に不適切で侵入させたくない
- 所有者：下流コンテキスト
- 動機：自衛・独立性の確保

### OHS/PL: 公開ホストサービス/公表された言語

上流コンテキストが複数の下流コンテキストのために、標準的なインターフェースを提供する構造。

- 選ぶ状況：
  - 複数の下流チームが同じ上流を使う
  - 上流チームが下流の多様なニーズに個別対応したくない
  - 標準的なAPIとモデルを公開して下流に使わせたい
- 所有者：上流コンテキスト
- 動機：サービス提供・スケーラビリティ

## DDDにおける契約に近い概念

### PL (Published Language) 自体が契約

PLはまさにインターフェース契約に最も近い概念

- PLが定義するもの：
  - データ形式（スキーマ）
  - バージョニング
  - 意味の定義（ドメイン言語による）
- 一般的なインターフェース契約との違い：
  - 技術的な仕様だけでなく、ドメインの意味まで含めて定義する
  - 「このフィールドが `business_date` と呼ばれる理由」までが契約の一部

### Customer/Supplier 関係における合意

DDDのCustomer/Supplier関係には暗黙的な契約がある

- Supplier（上流）の義務：
  - Customerのニーズを考慮して設計する
  - 破壊的変更を一方的に加えない
- Customer（下流）の権利：
  - 上流に要求を伝える
  - 変更の影響を事前に知る

### 補足：より明示的な「契約」の概念

- DDDの外の概念だが、DDDと組み合わせて使われるものとして Consumer-Driven Contract Testing がある
- これはOHS/PLとACLの境界での破壊的変更を防ぐ仕組みとして機能する

```
考え方：
　下流（Consumer）が「自分はこういう形式を期待する」という契約をテストとして定義する
　↓
　上流（Provider）はそのテストをパスすることを保証する
　↓
　PLの定義が壊れていないことが自動的に検証される

代表的なツール：
　Pact（コントラクトテストのデファクトスタンダード）
```

## 集約と値オブジェクトの判断基準

前提：同じデータでもコンテキストによって集約になることもあれば値オブジェクトになることもある

- 集約 (Aggregate) として扱う場合：
  - そのコンテキストで独立して操作される
  - IDで識別される必要がある
  - そのコンテキストの中心的な関心事
  - ライフサイクルを持つ（作成・更新・削除: mutable）
- 値オブジェクト (Value Object) として扱う場合：
  - 別の集約に従属している
  - IDで識別する必要がない
  - そのコンテキストでは参照されるだけ
  - 変更するなら別コンテキストで行う (immutable)

## 結果整合性とドメインイベント

集約の設計原則（1トランザクション1集約）を守るために、結果整合性とドメインイベントが必然的に必要になる

> [!NOTE]
> - 結果整合性：複数の集約をまたがる変更が即座に反映されないことを許容する設計
> - ドメインイベント：集約の状態変化を表現するイベント。これを他の集約やシステムに伝えることで、非同期に連携する
> - イベント駆動アーキテクチャ：ドメインイベントを中心にシステムを設計するアプローチ。集約間の結合度を下げ、スケーラビリティや柔軟性を向上させる

### なぜ必然なのか

- 集約の原則：
　- 1トランザクションで変更するのは1集約のみ
- 現実のビジネスロジック：
  - 例：計画と制御が直列で連携
　  -「計画が承認されたら制御に通知する」
  　- → 計画集約と制御集約を同時に変更したい
- 原則を守ると：

    ```
    同一トランザクションで両方変更できない
  　  ↓
　  どうするか？
  　  ↓
  　ドメインイベントで結果整合性を実現する
    ```

解決策：

1. 計画：計画集約を更新するトランザクションを完了
2. 計画：ドメインイベントを発行
3. 制御：イベントを受け取り自分のトランザクションで処理 → 最終的に整合（結果整合性）

### 一般的なイベント駆動アーキテクチャとの違い

- 一般的なイベント駆動の動機：技術的な理由
　- 疎結合にしたい
　- スケーラビリティを上げたい
　- 非同期処理をしたい
- Vernonが主張するドメインイベントの動機：ドメインの理由
　・集約の整合性境界を守るために必然的に必要
　・ビジネス上の出来事を明示的に表現する

### まとめると

```
集約の原則
　↓ を守ると
複数集約をまたぐ変更は同一トランザクションでできない
　↓ だから
ドメインイベントで結果整合性を実現するしかない
　↓ 結果として
イベント駆動アーキテクチャが自然に導かれる
```

## DDDにおける結果整合性

Vernonの考え方：「結果整合性」はあくまで整合性が最終的に取れればよいという意味

1. 強整合性
     - すべての集約が同一トランザクションで変更される
     - 計画と制御が同一トランザクションで実行される
2. 結果整合性
     - 集約ごとにトランザクションが分かれる
     - 計画が承認された後、制御は非同期に実行される（例:スケジュールされたジョブ）
     - ビジネス要件によっては、結果整合性で十分な場合もある

結果整合性の許容範囲をビジネス要件として明確にする必要がある。
「1.強整合性」が必要か「2.結果整合性」で十分かは、ドメインエキスパートへの重要な確認事項。

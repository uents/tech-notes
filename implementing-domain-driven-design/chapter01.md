# DDDへの誘い

## ドメイン駆動設計とは

ドメイン駆動設計（Domain-Driven Design, DDD）は、ソフトウェア開発の手法の一つで、複雑なビジネスドメインを理解し、そのドメインに基づいてソフトウェアを設計することを目的としている

### ドメイン駆動設計以外の設計手法

- トランザクションスクリプト
  - 手続き的にビジネスロジックを書くスタイル
  - 例えば「注文処理」という関数の中に在庫確認・決済・メール送信が全部ベタ書きされるイメージ
  - 小規模システムなら十分だがが、複雑になるほど破綻しやすい
- データ中心設計 (Database-First)
  - まずテーブル設計から始めて、それにコードを合わせていくスタイル
  - ビジネスの言葉よりDBの都合でモデルが決まるため、ドメインの概念がコードに反映されにくくなる
- 貧血ドメインモデル（Anemic Domain Model）
  - オブジェクト指向っぽく見えるが、クラスはデータの入れ物だけでロジックはServiceクラスに全部書かれているスタイル
  - Fowlerが「アンチパターン」と呼んだもので、DDDコミュニティでは批判的に扱われることが多い

## ユーザーストーリー

ユーザーストーリーは、ユーザーの視点からシステムの機能を表現する方法。一般的なフォーマットは以下の通り。

```
As a <ユーザーの役割>, I want <機能> so that <目的>.
```

> [!NOTE]
> * 「ユーザー」とあるが内部の「サービス」もユーザーストーリーの対象になることがある
> * 例えば「As a PaymentService, I want to validate credit card information so that I can process payments securely.」のように、システム内部のコンポーネント同士のやりとりを表すこともある

ユーザーストーリー数とDDD適用の関係は以下のように考えられる。

| ユーザーストーリー数 | DDD適用の必要性 |
|------------------|----------------|
| 数件以下            | DDDの適用は必要ない。データ構造がシンプルで、ビジネスロジックも単純な場合は、DDDの複雑さを導入するメリットが少ない。（データ主導でよい） |
| ~30程度 | シンプルなシステムであり、最低限のビジネスロジックしか持たないため、DDDの適用は必須ではない |
| 30~40程度 | ビジネスロジックが増え、ドメインの複雑さが増すため、DDDの適用を検討する価値がある |
| それ以上 | ビジネスロジックがさらに複雑になり、ドメインの理解が重要になるため、DDDの適用が強く推奨される |

## ユビキタス言語

ユビキタス言語（Ubiquitous Language）は、

1. ドメインエキスパートと開発者が共通して使用する言語（業務で使用する用語）
2. Bounded Context内で一貫して使用される言語

> [!NOTE]
> ユビキタス言語はチームが開発するドメインモデルで表現されるものであって、「業界全体で」「全プロジェクトで」共通の言語を指すわけではない。プロジェクトごとにユビキタス言語は異なる可能性がある

DDDやIDDDにはユビキタス言語の具体的な管理運用方法は記載されていない。要件定義書やシステム方式設計書に記載するのか、プロジェクトによってはWikiやドキュメント管理ツールを使用するような形か

**ユビキタス言語の例**

| 用語 | 英語 | 説明 |
|------|------|------|
| 顧客 | Customer | 商品やサービスを購入する人 |
| 注文 | Order | 顧客が商品を購入するためのリクエスト |
| 商品 | Product | 顧客が購入する対象 |

## 境界づけられたコンテキスト（Bounded Context）

Bounded Contextは、ユビキタス言語が有効に機能する境界を定義する概念。
同じ単語（例：`Customer`）でも、コンテキストが異なれば意味・属性・振る舞いが異なる場合がある。

- **境界の内側**：ユビキタス言語が一貫して適用され、ドメインモデルが整合している
- **境界の外側**：別のBounded Contextであり、言語・モデルは独立している

> [!NOTE]
> Bounded Context同士の関係はコンテキストマップ（Context Map）で表現する。詳細は2章以降で扱う

## コアドメイン（Core Domain）

ドメインはコアドメイン・支援サブドメイン・汎用サブドメインに分類される。どこがコアドメインかを明確にすることで、DDD適用の優先順位を判断できる。

> [!NOTE]
> 詳細は [2章](chapter02.md) で扱う

## DDDの採用価値

1. 組織として、ドメインに関する有用なモデルを獲得できる
2. 事業について、より洗練された正確な定義ができて、さらに深く理解できる
3. ドメインエキスパートが、ソフトウェア設計に貢献できる
4. よりよいユーザー体験を提供できる
5. モデルとモデルの間に、明確な境界を定められる
6. エンタープライズアーキテクチャが、より整理されたものになる
7. アジャイルでイテレーティブなモデリングを、継続的に行える
8. 戦略的な面でも戦術的な面でも、新しいツールを使える

> [!NOTE]
> * 戦略的設計: ドメインの分割や、コンテキストマップなど、システム全体の構造に関わる設計
> * 戦術的設計: エンティティ、集約、リポジトリなど、ドメインモデル・コンテキストの内部構造に関わる設計

**戦術的ツール**

- 集約 (Aggregate)
- エンティティ (Entity)
- 値オブジェクト (Value Object)
- サービス (Service)
- ドメインイベント (Domain Event)
- リポジトリ (Repository)

## 技術的負債

### 定義

- 本来の定義
  - 「今は最善でない設計を意図的に選択し、後で改善することを前提にした判断」です。つまり元々は意図的な戦略的判断を指す用語
  - 元々は Ward Cunningham が1992年に提唱した概念で、金融の「負債」をメタファーにしている
- 現在の一般的な使われ方
  - 実際には意図的でない負債も含めて広く使われている（Cunningham自身もこの拡大解釈を認めている）

### 技術的負債の分類

Martin Fowler が提唱した技術的負債の4象限

| | 意図的 | 無意図的 |
|---|---|---|
| 無謀 | 「設計を考える時間はない」 | 「レイヤー構造って何？」 |
| 慎重 | 「今はリリース優先、後で対処」 | 「あの設計の問題が後からわかった」 |

- 意図的×無謀：締め切り優先で意図的に手を抜く。最も有害
- 無意図的×無謀：知識不足や技術力不足から生まれる。気づかないまま蓄積する
- 意図的×慎重：リリース優先と明示した上で後で改善する合意がある。本来の意味に近い
- 無意図的×慎重：後から振り返って「あの設計はまずかった」とわかるもの。成長の証とも言える

> [!NOTE]
> Cunningham の技術的負債メタファーの延長として、技術的負債は放置すると利子が複利で膨らむと表現される。人員投入は元本を返済せず利子だけを払い続けている状態に近く、いずれ返済不能になる

### 技術的負債の発生要因

- 設計
  - 不適切な抽象化（Leaky Abstractionなど）
  - 蜜結合・低凝集
  - Seamのない設計
  - ドメインモデルとコードの乖離
- 知識
  - ドキュメント不足
  - 暗黙知の属人化
  - テスト欠如
- 依存関係
  - 古いライブラリの採用
  - 不要な外部依存
- テスト
  - カバレッジの不足
  - 実機なしでは動作しない (Seamのない構造に依存)

### 技術的負債と認知負荷の関係

認知負荷が高い状態では：

- 設計を深く考える余裕がなくなる
- とりあえず動けば良いという戦術的プログラミング（APoSDの言葉）に陥る
- レビューの質が下がり問題のあるコードが混入しやすくなる
- ドキュメントを書く余裕がなくなり暗黙知が増える

結果として技術的負債が加速度的に蓄積する。

### Agentic Coding 時代の DDD の採用価値

- 一人当たりのドメイン知識の幅が広くなる必要がある
- ドメインモデルの明文化・共有が重要になる
- DDDの語彙と設計が組織の共通言語として機能する

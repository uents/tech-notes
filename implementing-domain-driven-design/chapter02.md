# ドメイン、サブドメイン、境界づけられたコンテキスト

## ドメイン

特定のビジネスや活動の範囲。問題空間とも呼ばれる。例：eコマース、銀行業務、医療など

## サブドメイン

ドメイン内の特定の機能や関心事に焦点を当てた部分。例：注文管理、在庫管理、顧客管理など

- **コアドメイン（Core Domain）**：最も重要。独自のノウハウや競争優位性を持つ領域。DDDの投資対効果が最も高い
- **支援サブドメイン（Supporting Subdomain）**：コアドメインを補助するが、汎用品では代替できない領域
- **汎用サブドメイン（Generic Subdomain）**：既製品やSaaSで代替できる領域。内製する必要はない

サブドメインは「発見する」ものであり「設計する」ものではない。ドメインエキスパートとの対話やドメインの分析を通じて、自然に浮かび上がってくるもの

## 境界づけられたコンテキスト（Bounded Context）

ユビキタス言語が有効に機能する境界を定義する概念。
同じ単語（例：`Customer`）でも、コンテキストが異なれば意味・属性・振る舞いが異なる場合がある

- **境界の内側**：ユビキタス言語が一貫して適用され、ドメインモデルが整合している
- **境界の外側**：別のBounded Contextであり、言語・モデルは独立している

Bounded Context は、ソフトウェアの境界として「設計する」ものである。

### Bounded Context とサブドメインの関係性

- 理想的には、1つのサブドメインに対して1つのBounded Contextが存在
- ただし、現実的には１つのBounded Contextが複数のサブドメインを包含することもあるし、逆に1つのサブドメインが複数のBounded Contextに分割されることもある
- 例： レガシーシステムの都合で、注文管理サブドメインと顧客管理サブドメインが同じBounded Contextに存在する等

## 共有カーネル (Shared Kernel)

複数のBounded Contextが共有するモデルやコード等の共通部分。

- 変更時にすべてのBounded Contextに影響が及ぶ可能性があるため、共有カーネルの管理は慎重に行う
- 共有範囲が広ければ、Bounded Context同士の結合度が高くなり、独立性が損なわれるリスクがある

**共有カーネル と Platform Engineering の関係**

- 共有カーネルは、複数のBounded Contextで共通して使用されるコードやモデルを管理するための仕組み
- Platform Engineeringは、チーム全体で共通のプラットフォームやツールを提供することで、開発効率や品質を向上させるアプローチ
- 共有カーネルは、Platform Engineeringの一部として、共通のコードやモデルを管理する役割を果たすことができる

## 集約の重要性

集約は、ドメインモデルの中で一貫性を保つための重要な概念。
集約ルートを中心に、関連するエンティティや値オブジェクトをまとめることで、ドメインの複雑さを管理しやすくする。

- トランザクション境界を定義
  - 集約は「1トランザクションで変更してよい範囲」を定義する役割も持つ
- ドメインの知識を表現
  - 集約の境界は「これらは常に一緒に変更されるべき」というビジネスのルールを表現している

> [!NOTE]
> 集約の詳細（設計ルール・トランザクション境界・集約ルートの選び方など）は10章で扱う

**集約はあらゆるコンテキストに必要か？**

- 集約が重要になるコンテキスト
  - コアドメイン
    - ビジネスルールが複雑で、ドメインの一貫性を保つことが重要な領域 
    - 集約を適切に設計することで、ドメインの複雑さを管理しやすくなる
- 集約の重要性が下がるコンテキスト
  - 支援サブドメイン
    - コアドメインを補助するが、ビジネスルールが比較的単純な領域
    - 例えば、シンプルなCRUD操作が中心のコンテキストでは、集約を厳密に設計するより、トランザクションスクリプトなどのアプローチが適している場合もある
  - 汎用サブドメイン
    - 既製サービスで代替する場合は、そもそも自前でモデリングを行わない
    - ACLで外部サービスのモデルを翻訳する程度で十分な場合もある

## コンテキストマップ

コンテキストマップは、Bounded Context同士のモデルの関係性を表現する図。
「AはBに依存しており、Bの変更はAに影響を与える」といった関係性を表現することで、Bounded Context同士の結合度や独立性を理解しやすくする。

### 統合パターン

Bounded Context同士の関係性を表現するためのパターン。

| パターン名 | 英語 | 概要 |
|------------|------|------|
| 顧客/供給者 | Customer/Supplier | 上流（供給者）が下流（顧客）のニーズを考慮して開発する。上流側に優先権がある |
| 順応者 | Conformist | 下流が上流のモデルをそのまま受け入れる。上流側に交渉力がない場合に発生 |
| 腐敗防止層 | Anti-Corruption Layer (ACL) | 下流が上流のモデルを自分のモデルに翻訳する変換層を設ける。モデルの汚染を防ぐ |
| 公開ホストサービス | Open Host Service | 上流が公開APIを提供し、下流が自由に利用できる。プロトコルはドキュメント化される |
| 公表された言語 | Published Language | 共通のデータ交換フォーマット（JSONスキーマ等）を定義し、複数のContextで使用する |
| 共有カーネル | Shared Kernel | 複数のBounded Contextが共通のモデル・コードを共有する。変更時は全チームの合意が必要 |
| 別々の道 | Separate Ways | 統合コストが高く、それぞれ独立して実装する方が効率的な場合に選択する |
| 大きな泥団子 | Big Ball of Mud | 境界が曖昧で整理されていない既存システム。レガシー対応時に認識しておく必要がある |

> [!NOTE]
> * ここでの「上流」「下流」とは、誰が誰に影響を与えるかという関係性を指す。例えば、外部サービスが提供するAPIを利用する場合、外部サービスが上流で自分たちが下流になることが多い
> * 上流・下流の関係性（誰が誰に影響を与えるか）を意識してパターンを選択することが重要。ACLは外部サービスや汎用サブドメインとの接続時に特に有効

### 「エンタープライズアーキテクチャ」や「システムトポロジー」との違い

- コンテキストマップ： Bounded Context同士のモデルの関係性を表現する図
  - 「AはBに依存しており、Bの変更はAに影響を与える」といった関係性を表現
- システムトポロジー： システムの構成要素やコンポーネントの関係性を表現する図
  - 「AはBを呼ぶ」という事実を表現
- エンタープライズアーキテクチャ： 組織全体のシステム構成や技術スタックを俯瞰するためのアーキテクチャ

| 名前 | 関心事 |
|------|--------|
| コンテキストマップ | モデルとチームの関係性の地図 |
| システムトポロジー | 通信経路の地図 |
| エンタープライズアーキテクチャ | システム構成の地図 |

## まとめ

- ドメインは「発見する」ものであり、Bounded Contextは「設計する」もの
- 「ドメイン」「Bounded Context」「共有カーネル」の3つの概念を図示すると以下の通り


```
ビジネスの世界（発見する）
  ドメイン
    ├─ コアドメイン
    ├─ 支援サブドメイン
    └─ 汎用サブドメイン

        ↓ マッピング（ideally 1:1）

ソフトウェアの世界（設計する）
  Bounded Context A（顧客管理）
  Bounded Context B（注文管理）  ┐
  Bounded Context C（在庫管理）  ┘← 共有カーネル（A・B・Cで共有されるモデル）

  ↑コンテキストマップでBounded Context同士の関係性を表現する
```
